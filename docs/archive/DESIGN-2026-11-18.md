# 09 · 全方位游戏应用：设计与开发方案

> 依据：三个开源项目的代码级分析（`01`–`06`）、需求定版（`07`）、以及**在你这台机器 + 你的真实存档 + 32 GB 游戏文件上的实测**（`08`）。
> 本文是可执行的产品设计 + 工程方案，所有性能数字都来自本机实测，不是估值。

---

## 0. 摘要

**产品**：一个本地运行的「无人深空飞船/星球情报台」——搜、看、拿、分享，四件事闭环。

**三个决定性实测数字**（后续所有设计都围绕它们）：

| 数字 | 含义 |
|---|---|
| 系统生成 **0.039 s/系统**（热态，25 系统/秒） | 「找星球/找船池」可以做到交互级响应 |
| 单船 3D **0.4–1.2 s**（热）／5.8 s（首解包） | 3D 预览可实时，但必须做「解包预热 + 派生缓存」 |
| 搜索 **13–20 M seeds/s**（4 核稳态） | 按部件找种子是秒级；但**进程启动 9 s 会吃掉短任务**，必须常驻 worker |

**形态**：`本地网页 UI（127.0.0.1）+ Python 内核 + 常驻工作任务池 +（可选）游戏内实时通道`。
**不做**：注入 DLL、改玩家位置/货币、多人写入、跨型移植外观。

## 1. 产品定位与用户旅程

### 1.1 用户与场景
| 用户 | 想要 | 对应能力 |
|---|---|---|
| 找船党 | 「我想要这艘外观的拦截机」 | 按部件搜种子 → 3D 确认 → 写回存档/送进游戏 |
| 晒图党 | 「把我这 7 艘船拍成图/模型」 | 存档船图鉴 → 批量渲染 PNG / 导出 glb |
| 探索党 | 「找 Lush + 无哨兵 + dissonant 的星系」 | 星球扇扫 + 条件过滤 |
| 收藏党 | 「本星系会刷什么船」 | 系统面板（50 条船池 + 拦截机种子） |

### 1.2 四条主旅程（每条都对应已实测的链路）

```
① 找船：输入约束(船型+部件+涂装) → 搜索(job) → 结果网格(缩略图) → 选一艘 3D 预览
        → 决定：写回存档 / 送进游戏 / 导出 glb
② 看我的船：读存档(7 艘) → 图鉴(3D+部件表) → 与目标船并排对比 → 挑一艘当"模板"
③ 找星球：当前系统 or 输入 glyph/坐标 → 系统面板(行星表+船池) → 标记候选 → 批量扇扫
④ 分享：任意 ShipRef → 分享码(压缩的 type+seed+parts 哈希) → 别人粘进来即可还原预览
```

## 3. 系统架构

### 3.1 进程模型

```
┌───────────────────────────── 浏览器（127.0.0.1:随机端口） ─────────────────────────────┐
│  搜索 / 我的船 / 预览 / 星球 / 设置      （原生 JS，无框架；3D 用 WebGL 或 <model-viewer>）│
└───────────────────────────────────┬──────────────────────────────────────────────────┘
                                    │ JSON API（Host/Origin 校验，写操作 403 闸门）
┌───────────────────────────────────▼──────────────────────────────────────────────────┐
│ nmshunter-web（Flask，单进程，threaded）                                              │
│  ├── jobs：任务表（id/进度/ETA/取消），SSE 或 1 s 轮询                                │
│  ├── cache：三层缓存索引（版本指纹命名）                                              │
│  └── settings / lock / log                                                            │
└──────┬───────────────────────────────────┬───────────────────────────────┬────────────┘
       │ 进程内（只读数据）                │ 进程池（CPU 密集）            │ 可选外部通道
┌──────▼──────────┐              ┌─────────▼──────────────┐        ┌───────▼─────────┐
│ 数据层           │              │ worker pool（N=2）      │        │ live 代理        │
│ catalog/icons    │              │ · search（seed 扫描）   │        │ ReadProcessMemory│
│ pak 解包缓存     │              │ · system（emu 生成）    │        │ 模板槽写 seed    │
│ 存档读写         │              │ · model（几何+蒙皮）    │        │ （仅写入模板槽） │
└──────────────────┘              └────────────────────────┘        └─────────────────┘
```

**为什么是"常驻 worker pool"而不是"每请求开进程"**（实测）：
* 短任务：`workers=3` 跑 8.4 M seeds 用了 **8.94 s**（其中 ~9 s 是 3 个进程的启动 + 重复 import + 缓存校验）；`workers=1` 跑 65 k seeds 只要 **0.01 s**。
* 稳态：`workers=1` ≈ **13 M/s**，`workers=3` ≈ **20 M/s**（1.5×，4 核）。
* 结论：**每请求 spawn 是陷阱**；必须常驻 worker（启动一次，之后收任务），否则用户点"搜索"会先等 9 秒。

## 4. 七个关键技术决策（附实测依据）

| # | 决策 | 依据 | 代价 |
|---|---|---|---|
| D1 | **预览三级降级**：L0 缩略图 / L1 真 3D / L2 游戏内 | 无 pak 时退 L0（已验证）；有 pak 时 0.4–1.2 s 出模型 | UI 要能表达"当前是 L0 还是 L1" |
| D2 | **常驻 worker pool（N=2）** | spawn 9 s / 稳态 1.5× 加速 | 复杂度 + 内存（每人 262–274 MB） |
| D3 | **三层缓存，按版本指纹命名** | 版本指纹 `{exe:[size,mtime], paks:97}`；提取缓存现 72 MB | 缓存失效要可观测（"已重建"提示） |
| D4 | **版本三层 + 冒烟自检** | Gagarin 被闸门挡住（`08` §1）是反面教材 | 每次启动多 0.5 s |
| D5 | **写入协议：读→备份→改→原子写→回读→回滚** | 上游 `save.py:76` 非原子写 | 写路径更慢（可接受） |
| D6 | **一切长任务都是 job** | 搜索/扇扫/建模都可能 >1 s | 需要 job 表 + 取消语义 |
| D7 | **并发上限 2，串行化 IO** | 32 GB pak 在机械/网络盘上 IO 是瓶颈；RSS 262 MB/进程 | 峰值吞吐受限，但稳定 |

## 7. 前端设计

* **技术**：原生 JS + 原生 WebGL（或 `<model-viewer>` 嵌 glb），无构建链——与 Shipwright 一致，减少打包风险。
* **页面**：搜索 / 我的船 / 预览对比 / 星球 / 设置（五页，顶栏切换）。
* **性能手段**（来自实测）：结果网格用虚拟滚动（一屏 40 个缩略图，滚动才取 PNG）；3D 只在"选中项"构建；glb 走 ETag 缓存；`requestIdleCallback` 预热相邻项。
* **L0/L1 表达**：每张卡片右上角标 `3D` 或 `部件图`；不可用时明确写"未检测到游戏文件，显示部件缩略图"，而不是空白。
* **写入交互**：写按钮默认禁用 + 首次开启需在设置页确认；每次写弹"将备份到 `<path>.bak`"的二次确认；完成后显示"已读回校验通过"。

## 9. 版本跟进与降级矩阵（公开项目的生命线）

| 层 | 变更频率 | 检测方式 | 失败后行为 | 用户可见提示 |
|---|---|---|---|---|
| pak 容器 | 极低 | magic/索引自校验 | 3D 退 L0 | "游戏档案格式变更" |
| MBIN 布局 | 每年数次 | `gamemeta` 反射 + `(name_hash,guid)` | 3D 退 L0，存档照常 | "需要更新布局表" |
| exe 地址（systemgen） | 每次更新 | 冒烟：固定 UA → 比对已知行星/船池 | 星球模块禁用 | "系统生成暂不可用（版本未适配）" |
| 存档 JSON 键 | 偶发 | 读存档时字段校验 | 只读模式 | "存档字段变化，写回已禁用" |
| 内存模板槽 | 每次更新 | 多候选签名 + 结构自洽打分 | 实时通道禁用 | "实时通道暂不可用" |

**铁律**（来自 Gagarin 的教训）：**任何一层失效只关掉那一项功能，绝不整块停摆。**

## 10. 打包与分发

| 项 | 方案 |
|---|---|
| 打包 | PyInstaller `--onedir`（`--onefile` 启动慢且杀软误报更重）；`threading.stack_size(16MB)`；Windows 需清 CFG（上游踩过：exit 127） |
| 体积预估 | 上游代码 + numpy ≈ 60 MB；加 unicorn ≈ +17 MB；**游戏数据不进包**（首次运行从用户自己的 pak 解包，缓存 72 MB 起） |
| 首次运行 | 引导页：选游戏目录 → 指纹识别 → 解包预热（进度条，一次性 10–30 s）→ 选存档目录 |
| 更新 | GitHub Releases + `version.json`（build/size/sha256），程序内提示更新但**不自动替换**（避免 Gagarin 那种自我替换风险） |
| 许可 | 上游各自许可须核对（Shipwright 的 LICENSE、Gagarin 的字体 OFL）；本项目 MIT + 明确"非官方、可能损坏存档，先备份" |
| 免责 | 只支持单机；写入前自动备份；不碰多人 |

| 游戏更新导致 `systemgen` 偏移失效 | 高（每次更新） | 星球模块不可用 | 冒烟自检 + 分层降级 + 版本提示；不阻塞搜索/预览 |
| 32 GB pak 在慢盘上 IO 抖动 | 中 | 首次预览慢 | 预热 + 缓存 + 进度可见 + 可取消 |
| 4 核机器并发受限 | 高 | 扇扫/搜索慢 | 并发上限 2、任务队列、ETA 诚实 |
| 用户机器 Python 环境差异 | 中 | 启动失败 | 打包 onedir + 启动自检 + 明确报错 |
| 写存档损坏 | 低 | **高** | 备份 + 原子写 + 读回 + 回滚 + 只读默认 |
| 杀软误报（内存通道） | 高 | 用户流失 | 源码可跑、发布 hash、默认不启用内存通道 |
| 上游 Shipwright 变更/停更 | 中 | 维护成本 | 版本锁定 + 薄封装 + 关键路径有本地副本策略（必要时 fork 单文件） |

## 14. 明确不做

1. 注入游戏进程、改游戏代码（Gagarin 的 DLL 路线只作为"思路来源"，不复制其版本绑定）。
2. 改玩家位置/货币/物品/多人状态。
3. 跨型移植外观（`seed` 与 `type` 不可分离，见 `06` §3）。
4. 自动替换自身二进制（Gagarin 的自更新方式风险过高）。
5. 托管控件/账号：全部本地。

## 15. 演进方向（M6 之后）
